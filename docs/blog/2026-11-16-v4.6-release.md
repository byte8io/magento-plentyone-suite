# Magento PlentyONE Suite v4.6 Released - Hardened Order Sync, Localized Child Products & a Quieter Catalog

**Magento PlentyONE Suite v4.6** is the largest release since the Byte8 rebrand: 11 modules, 14 features and 43 fixes, most of them driven by incidents on live shops. The headline: **order sync no longer makes things worse when something goes wrong**. A failed payment capture no longer auto-closes an order, a PlentyONE rate limit stops the run instead of erroring every remaining order, cancellations are sent exactly once and never for a paid order, and exports whose count landed on a batch boundary stop looping forever. On the catalog side, **configurable children can now carry a localized name per store view**, generated child names stop being reshuffled, url key collisions are checked against real URLs per store view, and the import stops purging your full page cache for products that did not change. The item export **recovers from duplicated products, rate limits and half-created items**, the API client **shares one token across all processes**, and the connector now **reports its licence status in the admin**.

## Order sync that fails safely

A real-world sequence drove most of this work: a PayPal capture failed with HTTP 422 during an order import, the invoice step had already stamped the items as invoiced in memory, the shipment step persisted that dirty state, and Magento auto-closed the order - shipped, closed, never paid. The export then mapped "closed" to a PlentyONE cancel on an uncaptured order. v4.6 closes every link of that chain:

- **Processor failures roll back.** After any import processor fails, the order is restored to its persisted state and Magento's order registry is reset, so the shipment step never sees half-applied changes. A failed online capture is flagged **retryable** and the order parks as DEFERRED for the retry cron instead of needing a manual re-import.
- **Deferred documents survive unrelated errors.** A failure in another step of the same run used to overwrite the DEFERRED marker and strand the shipment or invoice forever. The retryable marker now always wins; the error stays visible in the saved messages.
- **Shipments wait for a clean order.** Before calling Magento's ShipOrder, the shipment processor defers when the order carries unsaved changes or the registry would hand over a diverging instance.

The order **export** got the same treatment:

- **No more paging loops.** The export now pages by entity id cursor. Offset paging skipped rows when exported orders dropped out of the status filter, and an export whose count was an exact multiple of the batch size never terminated.
- **Rate limits stop the run.** A PlentyONE throttle hands the current order back to its previous status (never error, keeping any PlentyONE id already created) and ends the run with a single warning naming the retry-after. Previously every remaining order fired, failed and sat in error until someone re-queued it.
- **Cancellations go out once, and never for paid orders.** A successful cancel is stamped on the order so a re-export cannot undo a status change made by hand in PlentyONE. A PlentyONE order with an approved payment, a paid amount or a status at or above a configurable threshold (default 7, goods dispatched) is never cancelled from Magento. Both guards are new profile options, on by default.
- **No phantom payments.** A cancelled order with nothing captured no longer posts its expired authorisation as a full-amount payment on every run.
- **Forced exports take the processing claim too**, so two admin runs over the same set no longer both export every order.
- **Large mass exports are queued.** Selecting more than 10 orders in the sales grid publishes them to the `plenty.order.export.processor` queue and returns immediately, instead of holding the admin session lock for minutes and inviting repeat clicks.
- **Order attribute filter guard.** Orders fulfilled outside PlentyONE (for example flagged by a separate CSV channel) can be excluded from export by `sales_order` attribute conditions configured per export profile; they are marked SKIPPED with a notice.

## Configurable children: localized names, kept as written

- **Localize child product names per store view** (new import option, default off). A child that is visible individually takes the item name of each store view's PlentyONE language, with that store's option values appended, so url keys and rewrites are built per store view. A property mapped to the name still wins wherever it provides a translation; stores it does not cover keep the localized name instead of collapsing to the default store.
- **Use Magento option labels in child product names** (new import option, default off). A value with no PlentyONE name in the store's language falls back to the store label of the matching Magento option before the default name.
- **Generated names are no longer reshuffled.** The old logic removed the option value from wherever it stood in the variation name and re-appended it at the end: "Blue Shirt Classic" became "Shirt Classic Blue". A value in another case, with punctuation or made of several words was appended a second time. The imported name is now kept as written and a value is appended only when none of its names, in any language, is already present as a whole word.
- **Attribute set inheritance.** A new child variation with no attribute set property in PlentyONE, and none on its main variation, now inherits the attribute set of the parent product in Magento instead of dropping to the profile default. Existing children keep their set.

## URL keys and rewrites: per store view, and safe

- **Collisions are checked against real URLs.** The import now checks a candidate url key against the `url_rewrite` table - categories, CMS pages, custom redirects, another product's 301 - not just other products' url_key values, per imported store view. New option "Check URL Key Against URL Rewrites", default on. The SKU suffix is the re-checked last resort; the option is renamed to **"Add SKU Suffix On Duplicate URL Key"** because it never reacted to a persist-time error.
- **Store-level url keys survive.** When an import gives a store view no url key (for example its localized name was not collected), the store's existing store-level key and rewrites are kept instead of being rebuilt from the default key. New option "Keep Store URL Key When Not Imported", default on.
- **Live rewrites are no longer deleted.** The conflict retry compared int ids against string ids, so every live product counted as an orphan and a persist conflict wiped the product's own canonical rewrites, and could strip another product's. Fixed, and the conflict error now names the colliding paths and the options that resolve them.
- **Visibility is resolved from what the import persists.** A child made visible in Magento and excluded from the import never received rewrites; a parent hidden in Magento kept receiving them. Both are fixed, along with an "Array to string conversion" failure on nested visibility values.

## A quieter, lighter import

- **No more full page cache purges for unchanged products.** With indexers in "Update on Schedule" mode, every post-batch indexer (EAV, price, flat, category-product, stock) now defers to the cron instead of force-reindexing the whole batch. One client measured an identical-data import at **141 cache purges before, 0 after**. "Update on Save" is unaffected.
- **No more useless Varnish bans.** The connector's internal mirror, queue, config and log entities no longer emit frontend cache identities. One shop saw about 7,000 no-op bans a day from order-history saves alone.
- **Memory stays flat.** Three per-run caches in the item import (reserved url keys, stock items, bundle option titles) grew for the whole run; they are now reset at every batch boundary via a new `BatchResetInterface` in `module-profile`.
- **Cron defaults move off busy slots** across all modules (:07, :11, :19, :23 and so on instead of :00 and :30), and disabled connector jobs are no longer scheduled as hourly no-ops.
- **Category export stops re-running.** The item export's category cache read the wrong table, saw every category as missing and re-ran the category export on every run.
- **Stock export queue metadata stops growing** (per-run source and warehouse ids reset, bookings audit log capped at 20 entries).

## Item export: duplicates, rate limits and half-created items

- **Duplicated products keep their hands off the source.** Magento's product copier copies the PlentyONE item and variation ids onto the duplicate, so the next export overwrote the source variation. Both ids are now cleared when a product is duplicated. A new integrity check, `plenty:item:check-integrity`, also lists any products that already share one variation id, and the export refuses to send conflicting commands in the same batch.
- **Existing products stop looping.** Existing products and configurable children never had their queue row written, stayed pending and were re-exported every run. Fixed, plus a new attempts counter moves rows that reach 5 runs without a result to error with an explanatory message.
- **Rate limits stop the run** here too: remaining batches are deferred instead of sent, and the products go back to pending.
- **Children export all their attributes.** Barcodes, properties, dimensions and prices were unloaded on configurable children and exported empty. An empty barcode is no longer sent (PlentyONE rejected the whole variation with "barcodes.0.code muss ausgefüllt sein").
- **Half-created items show as error**, not warning, so they are visible in the queue grid; a re-export updates the created item instead of duplicating it.
- **Restored admin observers.** Product save and delete in the admin queue the product for export again, as they did before the module consolidation.

## API client: one token for all processes

PlentyONE's September 2026 authentication changes exposed two gaps. Every queue consumer and cron refreshed the shared token independently; the first refresh rotated it, every sibling got `invalid_grant` and fell back to a credential login, each consuming a PlentyONE session - one shop had 20 of 30 sessions in use for a single API user. And `/rest/login/refresh` can issue a token pair with empty scopes that strands the client. v4.6:

- takes a **cross-process lock** around authentication so exactly one process refreshes, and siblings adopt the already-refreshed token without an API call;
- **refuses scope-less refresh tokens** and falls back to a credential login;
- re-arms the re-authentication flag per request, so a long-running consumer recovers from a 401 without a restart;
- records **concurrent session usage** reported by the login response;
- gives `plenty:client:token` **`--login`** and **`--flush`** for incident recovery without manual SQL.

## Licence and configuration

- **Licence status in the admin.** Stores → Configuration → PlentyONE Integration → License now shows whether the key is present, the last successful heartbeat or last error, your plan and tier, and current websites, synced SKUs and exported orders against the plan limits. An admin system message appears while the key is missing, rejected or the last heartbeat failed. `plenty:system:check` gains a Licence section.
- **Heartbeat retries daily** after a failure instead of after 30 days, and reports the installed suite release rather than a module version. While no licence key is configured, an anonymous daily install ping (product, domain, versions - no counts, no key) lets Byte8 see the install exists.
- **`app/etc/env.php` is honoured** for the licence key and client credentials, with precedence over the database. CI/CD-injected secrets work, and a production dump restored to staging no longer points at the production PlentyONE account. Credentials and tokens are declared sensitive, so `app:config:dump` excludes them.

## Smaller fixes worth knowing

- `country_of_manufacture` and other string-keyed source-model attributes imported as 0 with an "invalid option: 0" warning - fixed.
- The weekly or daily one-time full collect+import fired on the wrong day because the schedule compared day-of-month only - fixed.
- The "Create Referrer" modal appeared to do nothing: it posted the name under a field the backend did not read, and never showed the error - both fixed.
- The profile schedule grid's mass status action silently failed under strict types - fixed.
- Stock status reconcile logs SKU lists only in a new debug mode; otherwise counts, and only when something was healed.
- Notification cleanup cron moves off the 02:00 slot.

## Upgrade Guide

```bash
composer require byte8/magento-plentyone-suite:^4.6

bin/magento setup:upgrade
bin/magento setup:di:compile
bin/magento cache:flush
```

**This release contains a schema change**: `plenty_item_export_queue` gains an `attempts` column, so `setup:upgrade` is required. Behaviours worth noting on upgrade:

- **Cancellation guards are on by default.** Orders with an approved or paid payment, or at PlentyONE status 7 or above, are no longer cancelled from Magento. Adjust *Cancel Skip When Paid* and *Cancel Status Threshold* in the order export profile if your flow needs it (threshold 0 disables).
- **Mass exports above 10 orders need the consumer.** Make sure `plenty.order.export.processor` runs via cron consumers or a process manager; the admin returns immediately and the queue does the work.
- **Scheduled indexers now really defer.** If your indexers are in "Update on Schedule" mode, imported changes reach the storefront with the indexer cron, not instantly. Switch to "Update on Save" if you rely on immediate visibility.
- **Two new url key options are on by default** ("Check URL Key Against URL Rewrites", "Keep Store URL Key When Not Imported"). The SKU suffix option is renamed; its stored value is unchanged.
- **Child name localization is opt-in.** Enable "Localize child product names per store view" and, if needed, "Use Magento option labels in child product names" under the configurable product group of the import profile. Both only apply while "System generated child product name" is on.
- **Cron slots change.** Default schedules move off :00 and :30; a custom cron expression in your configuration is untouched.
- **Export rows capped at 5 attempts** are moved to error with a message. Re-queue them once the cause is fixed.
- **Run the integrity check once** after upgrading: `bin/magento plenty:item:check-integrity` lists products that share a variation id so you can unmap the duplicates.
- **No licence key configured?** The connector sends an anonymous daily install ping and shows an admin message until the key is set.
